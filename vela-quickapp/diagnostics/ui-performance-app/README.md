# JSLab UI 真机性能诊断 v5

包名 `icu.ccicc.jslab.uiperf`，包版本仍为 **1.0.2 / versionCode 3**。
Vela 支持同版本覆盖安装；按用户约定不自动提升版本号。首页的 v5 只表示测试方案轮次。
本轮比较动态样式字符串与对象绑定，已收到真机结果：游戏 E 中位数 234 → 183 ms，16 格 409 → 319 ms。
按用户要求，后续优化已合并收尾，不再逐项发布新的诊断轮次。以下保留 v5 的使用和构建说明供复现。
当前引擎优化原则与验证入口见 [UI 性能建议](../../docs/ui-performance.md)。

## 在设备上测试

1. 覆盖安装 `dist/icu.ccicc.jslab.uiperf.release.1.0.2.rpk`，确认首页显示“UI 性能诊断 v5”。
2. 点击“开始自动测试”，保持屏幕亮起，不触摸、不滚动、不切换应用。预计 1–3 分钟。
3. 8 个场景，正序/逆序各一轮；每轮每场景 2 次预热、8 次采样，最终每场景 16 个样本。
4. 完成后发回 **5 页照片或 OCR**。无需设备 JSON、私有文件或调试日志。
5. 可选“手动点击 A/B”：依次比较“字符串/2048”和“对象样式/2048”。
   每组慢慢点 5–10 次“点此测试”，通过“切换方案”切换，最后点“完成”。

结果仅保存在本次运行的内存里，拍照前不要关闭应用或启动新一轮测试。
点“菜单”后仍可点“查看结果（拍照）”。切后台/返回可以停止测试。
测试请求常亮，完成、停止或离开时释放，不改屏幕亮度。
不依赖 `$nextTick`，不联网、不振动、不声明 `system.file`。
手动覆盖层有额外组件，手动数据只在手动组内比较。

主程序可同版本覆盖安装本仓库 `../../dist/icu.ccicc.jslab.release.2.0.0.rpk`，
另外体验原有 2048 的方向键、新局、退出，以及颜色和布局是否正常。

## 比较内容

| 对照 | 目的 |
| --- | --- |
| 字符串/1 格、对象样式/1 格 | 少量字段变化时的样式处理成本 |
| 字符串/16 格、对象样式/16 格 | 同时改变 16 格文字及背景 |
| 字符串/只背景、对象样式/只背景 | 聚焦 v4 中更慢的背景更新路径 |
| 字符串/2048、对象样式/2048 | 相同随机种子与方向序列下的实际游戏更新 |

每对都使用生产编译器、`createUiPublisher` 和同一响应式列表，每格原地更新变化字段。
对象模板从字符串模板生成，原生节点、for/tid、条件分支、几何、事件和样式结果保持一致，
只改变动态样式表达形式。所有场景都是相同的 24 个节点，预热后不更换节点对象。
本轮不启用 v4 的固定绑定。

工具链会在动态样式表达式外围调用 `$translateStyle$`：字符串需要分割、正则解析、键名转换及组装对象，
对象输入直接返回。对象绑定仍有表达式求值、对象构造和后续框架更新，不能预先保证性能提升幅度。

本轮继续使用诊断 v2 冻结的 2048 脚本，保留历次实验的可比性。
主程序后来更新的经典颜色和十字键不在这个对照脚本内；不要把诊断数字直接当作新版示例的完整实测。

## 指标解释

照片显示各阶段的中位数/最大值，单位 ms：

- J：操作开始到引擎刷新后的微任务边界，可能包含这之前已经执行的框架任务。
- E：操作开始到首个 `setTimeout(0)` 回调。
- V/C：描述构造 / 布局编译、节点比较与回调刷新。
- P：数据发布。每对使用相同生产提交器，没有旧版提交数量统计。
- Y：再一个 `setTimeout(0)` 的等待。
- **W：每次样本直接测量 J 结束到 E 的等待，再统计中位数/最大值。**

W 不通过相减两个汇总中位数计算。J/E/W 都不是屏幕显示完成时间，也不是原生绘制耗时或帧率。
照片中 W 替代原来的 O；100 ms 采样间隔超时 O 仍记录在可选日志里。
所有场景都有 100 ms 间隔；测量期间不更新进度、不输出日志、不写文件。
整数毫秒计时中，0 ms 表示小于时钟精度。最大值来自少量样本，不是长期最坏情况保证。
可选日志前缀为 `UI_PERF_V5`，不是必需的结果提交方式。

## 如何解释结果

- 对象组 E/W 在多组对照中明显更低：样式字符串处理确实影响完整更新链路。
- 对象组只有 J 更低：结合 E 判断总体收益，不能把不同阶段的中位数直接拆加。
- 各组接近：继续调查框架样式比较和底层更新，不能凭 timer 指标认定某个绘制函数慢。
- 诊断明显改善但主程序仍很慢：检查主程序集成环境与新版示例的字段变化数量。

## 本地验证与构建

从本目录执行：

```powershell
npm test
npm run release
```

`pretest`、`prebuild`、`prerelease` 会同步生产引擎到 `src/utils/optimized/`，更新 SHA256，
同时记录当前生产 `run.ux` 的 SHA256；`source-snapshot.json` 原始 `run-ui.ux` 哈希仅作为旧版测量基线保留。`scripts/sync-fixed-template.cjs` 生成 v4 的 24 个固定绑定
及 v5 的对象样式模板；`style-bindings.cjs` 只用于构建，不会进入设备运行代码。
原始基线 `uiLayout.js`、`uiRuntime.js`、`ui2048Example.js` 保持不变；
原始 `CASES`、v3 `RETEST_CASES` 与 v4 `FOCUS_CASES` 保留，当前页面使用 `STYLE_CASES`。
单独复制本目录时，可使用已附带的优化引擎快照。

本地测试覆盖字符串/对象和列表/固定绑定 40 步逐帧等价、节点身份、单字段隔离、
模板结构及工具链样式求值一致、异步错误、原始基线哈希、无 nextTick 的自动/手动流程与 5 页报告。
主项目另对运行页全部 19 处样式的值、单位及响应式依赖读取进行等价验证。
桌面测试和构建通过不等于设备验证。

在仓库内可使用上级工具链，单独复制时先安装开发依赖。
release 使用本目录已有 `sign/private.pem` 和 `sign/certificate.pem`；构建不会部署、连接设备或启动模拟器。
构建产物与签名材料已忽略。主程序保持 1.9.3，诊断程序保持 1.0.2。
旧诊断包分别保存在 `dist/v3/` 和 `dist/v4/`，当前 `dist/` 根目录放置 v5。
该根目录 RPK 仍是用户已测的 v5（SHA256 `15b9dd5a17e5b918f98c92dd63eb04852da05bd3821e64acf0bd33a3deb56cb4`），
收尾时没有重打诊断包。源码测试/构建钩子会同步最新生产编译器，因此再次构建的包不等于这份已测包。
已测 v5 编译器另冻结在主项目 `tests/fixtures/uiLayout-v5.js`，最终版与其在本地对照。
