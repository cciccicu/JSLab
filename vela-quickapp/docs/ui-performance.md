# UI v2 性能验证记录

2026-09-18，Windows / Node v24.19.0。基线为提交
`3a0a6d719f11542f010dd6eac4d979d16f023383` 的 UI v1 运行器。

复现：在 vela-quickapp 运行：

```powershell
node tests/benchUi.cjs 3a0a6d719f11542f010dd6eac4d979d16f023383
npm run test:ui
```

基准使用20个文本节点、4个signal、每项2000轮；先预热300轮。
一项signal影响5个节点。原生API用桩函数统计调用；不连接设备。
JS耗时包含描述构造、归一化和布局，但不包含真实Vela渲染、布局桥接或二维码编码。

| 场景 | v1 / v2 JS耗时 | v1 / v2 render执行次数 | v1 / v2 提交的节点对象 | v1 / v2 尺寸查询次数 |
| --- | --- | --- | --- | --- |
| 重复写相同值 | 24.82 / 0.32 ms | 2000 / 0 | 40000 / 0 | 2000 / 0 |
| 每轮1个signal变化 | 26.27 / 34.13 ms | 2000 / 2000 | 40000 / 10000 | 2000 / 0 |
| 每轮4个signal变化 | 70.01 / 42.93 ms | 8000 / 2000 | 160000 / 40000 | 8000 / 0 |

“提交的节点对象”是JS层替换/提交的数据对象数量，不是原生重绘次数或帧数。
表中的单次耗时用于说明成本方向，桌面JIT、系统负载会影响数值。
一次signal更新时，通用布局和差异比较令JS耗时增加约30%；同时数据提交减少75%，移除了原生尺寸查询。
多项signal更新时，合并重绘降低了总JS工作量。不能据此断言所有场景或真机都更快。

## 已落实的开销控制

- 无变化的signal不触发渲染；同一同步调用中的变化合并到一个微任务。
- 回调和渲染函数保存在非响应式session，避免交给Vela深度观察。
- 未变化叶子复用归一化缓存与节点对象；稳定拓扑下只splice改变的节点。
- 缓存仅保留当前一轮叶子，删除的id不会累计。缓存不保存事件回调。
- row/column/stack默认没有原生容器，只有背景需要额外绘制节点。
- grid与buttonRow展开后不再保留原生行容器。
- 编译时检查40个声明节点、4层嵌套、160个绘制节点、2个二维码上限。
- 滚动高度直接来自布局，不再每次调用getScrollRect。
- 二维码值、位置、颜色与尺寸未变时保持对象引用；页面集成测试确认不会splice该节点。

## 验证边界

12项UI行为测试覆盖嵌套布局、预算与循环引用、颜色、二维码复用、状态合并、
更新后的回调、异步异常、缓存几何失效、页面差异提交、内置模板和2048示例。
另通过快应用完整测试、lint与release构建。

未测手环端原生堆内存、实际帧率、不同字体下的文本断行、二维码扫码距离。
自动文本行数保守估算，不使用原生字体测量；精确界面推荐显式lines/lineHeight。
生命周期管理按本次范围维持原样。
