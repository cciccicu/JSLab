**1. [P1] 并发存储操作基于旧快照，成功返回后仍会丢数据**

位置：`src/utils/runtime/scriptData.js:95`；写入队列位于同文件第 63 行，删除和清空入口分别位于第 103、110 行。

`set` 先执行 `load → clone → 修改`，随后才进入 `persist` 的写入队列。队列只保证原生文件写操作依次进行，没有保证后一个操作读取前一个操作提交后的数据。因此多个调用会分别生成完整的旧根对象副本，最后一个写入覆盖前一个结果。

最小触发方式：

```js
await Promise.all([
  script.data.set('a', 1),
  script.data.set('b', 2)
]);
await script.data.all();
// 实际：{ b: 2 }
// 预期：{ a: 1, b: 2 }
```

复现中两次 Promise 均成功，文件先写入包含 `a` 的命名空间，再被只包含 `b` 的版本覆盖。换成两个不同脚本的存储实例，依然可以丢掉其中一个脚本的数据，因为所有命名空间共用同一个根 JSON 文件。`config`、`delete`、`clear` 使用相同机制，也受影响。

修复建议：将完整的“读取最新已提交数据 → 克隆 → 修改 → 校验 → 持久化”放进同一事务队列。前一次失败不能永久堵住后续操作，缓存只在写入成功后提交。不要仅给 `file.writeText` 加更多排队逻辑。

回归重点：同脚本并发 set、跨脚本并发 set、set 与 delete/clear 交错、写入失败后的下一次成功操作。

**2. [P2] 网格和加权横排可以输出负宽度或零宽度**

位置：`src/utils/runtime/uiLayout.js:156`、`src/utils/runtime/uiLayout.js:177`。

网格计算 `(inner - gap * (columns - 1)) / columns` 后没有检查结果。横排只检查剩余总宽度，没有检查每个 flex 子项分配并取整后的宽度。单独合法的参数组合，可以产生不合法的绘制几何。

```js
compileUi({
  kind: 'grid', id: 'g', width: 40, columns: 4, gap: 48,
  items: ['1', '2', '3', '4']
}, 12).nodes.map(node => node.width);
// 实际：[-26, -26, -26, -26]，没有报错

compileUi({
  kind: 'row', width: 100, gap: 0,
  children: [
    { kind: 'text', text: 'small', flex: 0.1 },
    { kind: 'text', text: 'large', flex: 100 }
  ]
}, 12).nodes.map(node => node.width);
// 实际：[0, 100]，第一个节点不可见
```

影响是无效几何或消失的内容/点击区域。**没有证据据此宣称会导致原生崩溃。**

修复建议：在进入子节点测量前验证网格的可分配宽度；对 flex 分配后的最终像素宽度验证下限。与目前“row 宽度不足就报错、保留上一幅有效界面”的规则一致，不需要增加新的布局算法。

回归重点：大间距窄网格、极端合法 flex 比例、嵌套窄容器，确保所有绘制宽度均为正数或编译明确失败。

**3. [P2] 自动行数缓存跨组件类型复用，导致布局依赖历史**

位置：`src/utils/runtime/uiLayout.js:264`。

行数复用条件只比较文本、取整后的宽度和字号。按钮测量时会扣除 16px 水平内边距，普通文本不会，但缓存条件没有包含组件类型或有效文本宽度。

```js
const label = {
  kind: 'text', id: 'same', width: 100, size: 24, text: '一二三四'
};
const first = compileUi(label, 12);
const button = { ...label, kind: 'button' };
const warm = compileUi(button, 12, first.nodes, first.cache).nodes[0];
const cold = compileUi(button, 12).nodes[0];
// warm：lines = 1，height = 64
// cold：lines = 2，height = 80
```

同一个最终界面，是否显示过同 id 的普通文本会改变按钮的行数预算和高度，可能截断按钮文字。原始浮点分配宽度与取整宽度之间的差异，也应纳入有效内容宽度的考虑。

修复建议：用实际参与断行估算的内容宽度和组件类型约束复用。直接限制不跨类型复用，也能以很小改动修复上述触发条件。

回归重点：稳定 id 下 text/button 互换、内边距影响、自动行数与显式 lines 切换；最终输出应与无缓存编译一致。

**4. [P2] 通用叶节点缓存将可变对象引用当作不变文本**

位置：`src/utils/runtime/uiLayout.js:225`，输入快照位于第 233 行。

通用叶节点把原始属性浅复制进缓存，并按引用判断是否变化。文本参数允许 `unknown`，最终使用 `String(value)`，因此同一对象的字符串表示可以改变。网格专用缓存已经排除对象/函数输入，通用叶节点没有采用相同限制。

```js
let label = 'before';
const value = { toString: () => label };
const view = { kind: 'text', id: 'mutable', text: value };
const first = compileUi(view, 12);
label = 'after';
compileUi(view, 12, first.nodes, first.cache).nodes[0].text; // before
compileUi(view, 12).nodes[0].text;                         // after
```

可变数组也有同类问题；重新构造描述对象但继续使用同一个文本值引用，依然会命中缓存。这里已显式重新编译，所以与文档中“相同引用的 signal.set 不触发刷新”的约定不同：调用 `ui.refresh()` 也无法修正旧文本。

修复建议：与网格保持一致，对参与输出的对象/函数输入不启用原始输入缓存，或保存规范化后的值。无需引入深比较、任意对象序列化或复杂依赖追踪。

回归重点：普通字符串仍命中缓存，可变数组和自定义 toString 对象在显式 refresh 后更新；回调继续独立更新。

**5. [P2] 发布失败后仍把新帧视为已提交，下一次刷新无法重试**

位置：`src/utils/runtime/uiRuntime.js:25`、`src/utils/runtime/uiRuntime.js:30`；另需联动检查 `uiPublisher.js:50` 和 `run-ui.ux:107`。

session 在调用 `host.publish` 前就更新了 cache、handlers 和 nodes。若宿主提交抛出异常，错误会显示，但下一次刷新将新结果与尚未真正显示的新 nodes 比较，判定为没有变化。

补充复现采用与页面一致的 `changed` 门控宿主：

1. 成功显示文本 `0`。
2. 改为 `1`，注入一次应用新节点之前的发布异常。
3. 调用 `ui.refresh()`。

实际三次 `changed` 为 `[true, true, false]`，最终显示仍为 `0`。同时事件处理器也可能已经切换为新帧的处理器，与旧画面不一致。

这是已用故障注入证明的恢复缺陷，**不是声称已在手环上观察到提交异常**。此外，发布器内部在返回新数组时就更新 `previous`，早于页面的 `this.uiNodes = next`；只调整 session 的赋值顺序还不足以覆盖数组赋值失败。

修复建议：定义清楚“编译完成”和“宿主提交成功”的边界，成功后才提交相关快照；桥接提交中途失败时，令发布器失效，并允许下一次进行完整提交。无需实现通用响应式事务回滚，但重试不能被旧缓存短路。

回归重点：在首次发布、字段更新、数组替换处分别注入一次异常，随后重试能恢复，并保证有效画面与事件处理器对应。

**6. [P2] 回调先更新状态再抛错，排队的刷新会立即清除错误提示**

位置：`src/pages/workspace/run-ui/run-ui.ux:109`。

所有成功发布都会执行 `this.error = ''`，包括发生错误前已经排队的 signal 刷新。用实际页面脚本、session 和 publisher，替换系统接口与定时器后复现：

```js
const n = ui.signal(0);
ui.render(() => [
  ui.text(n.get(), { id: 'n' }),
  ui.button('go', () => {
    n.set(1);
    throw new Error('after state update');
  }, { id: 'go' })
]);
```

调用按钮处理方法后，`page.error` 立即为 `Error: after state update`；等待一个 Promise 微任务后变为 `''`。错误可能在设备有机会显示它之前就消失，用户只看到状态变动或异常后的残留画面。

修复建议：将错误的清除与明确的恢复行为关联，例如用户确认、重新运行，或错误发生后明确发起的新一次渲染；不要让出错前排队的刷新自动确认错误已恢复。需要同时考虑错误卡片高度及滚动位置。

回归重点：状态更新后同步抛错、Promise 拒绝与排队刷新相邻发生、明确恢复后正常清除错误；正常无错误的刷新保持原有开销。

**7. [P2] 存储字典错误处理 constructor 和 __proto__ 等字符串键**

位置：`src/utils/runtime/scriptData.js:89`、`src/utils/runtime/scriptData.js:98`。

API 接受字符串键，但内部使用普通 `{}` 字典。读取未检查自有属性，写入直接使用下标赋值。

```js
await script.data.get('constructor', 'missing');
// 实际：读取到继承的构造函数，JSON 克隆时抛错；没有返回 fallback

await script.data.set('__proto__', { value: 1 });
await script.data.all();
// 实际：set 成功返回，但 all 为 {}，没有保存指定键
```

`__proto__` 的赋值改变的是这个局部字典的原型。这里**不认定为全局原型污染或沙箱逃逸**，确认的影响是合法键无法正确读写、成功保存的承诺不成立。

修复建议：读取使用自有属性判断，写入使用能保留任意字符串键的字典操作。必须验证 JSON 克隆及文件重新加载后的行为；只把最初的 `{}` 改成无原型对象，经过 JSON 克隆后仍可能重新出现问题。也可以明确拒绝保留键，但不能静默成功。

回归重点：`constructor`、`toString`、`__proto__` 的读写删除和重新加载，同时验证普通键、fallback 与 config。

**8. [P3] README 仍将用户引向旧版 UI API 文档**

位置：`README.md:27`；旧规则位于 `docs/UI_API.md:119`，当前规则位于 `docs/ui-api.md:113`。

README 的“完整 UI 脚本说明”指向 `docs/UI_API.md`。该文件仍写“最多保留 40 个根组件”，而现实现会统计布局和 buttonRow 按钮等声明节点并在超限时报错；v2 布局及合并刷新语义在另一份 `docs/ui-api.md` 中。

两文件区别包含下划线与连字符，不是仅大小写不同。用户正常沿 README 阅读即可进入过期文档，可能写出超预算脚本或遗漏已支持的功能。

修复建议：README、内置帮助及其他公开入口统一指向 v2 文档，旧文档显式标明历史版本并引导到新版。维护一份权威说明，避免继续复制 API 规则。

**其他方面的判断与边界**

| 方面 | 审查判断 |
| --- | --- |
| 性能方向 | 字段更新、独立编译快照、稳定节点身份、对象样式绑定值得保留。没有依据退回 splice 或引入专用 2048 渲染器。 |
| 缓存与内存 | 缓存随当前帧构建，删除节点不会一直积累；函数和 session 放在响应式数据外，销毁时清理 session。应修正缓存有效性，不需要增加深比较。 |
| 事件 | 视觉字段不变时仍更新回调，这能避免旧闭包；失活 session 的调用及回调错误有保护。未发现需要恢复旧回调存放方式的理由。 |
| 输入预算 | 声明数、展开绘制数、深度、重复 id、二维码数量均有约束；不能据此推导所有几何参数组合都安全，见问题 2。 |
| 样式与原生接口 | 已核对对象样式、slider/switch 事件参数、scroll API；未将 Vela 支持的 img 简写误判成 HTML 标签问题。颜色支持不限于 tone 预设，按钮可使用 stack 坐标布局。 |
| 文本与布局能力 | 行数是保守估算，不是字体测量；ASCII 可能多留空白，固定高度会裁剪。这是已记录的取舍，精确面板可显式给 lines/height。 |
| 异步交互 | 没有通用 disabled/busy 或自动防重复，脚本需自行检查忙碌状态；文档已说明，不将其直接列为引擎缺陷。 |
| 生命周期 | 用户创建的计时器和系统订阅由脚本管理，已有文档说明。页面退出不等于自动终止任意 JS 任务；不宜未经 API 设计就统一拦截全部系统调用。 |
| 信任边界 | 用户脚本通过 new Function 在共享 JS 环境执行，并可使用暴露的原生接口，不能当作不可信代码沙箱。当前文档没有宣称脚本间强隔离，本报告不据此虚构安全漏洞。 |
| 存储规模 | 每次修改复制并重写共享根 JSON，成本会随已存脚本数据增长；现有单项/命名空间限制不等于全库大小限制。尚无数据证明它是当前 2048 卡顿主因，先修正确性，避免推测性重构。 |

最近一轮设备对照中，2048 字符串样式与对象样式的 E 中位数为 234ms 和 183ms，对象样式有明确收益。对象样式的 J 为 58ms、W 为 124ms，说明仅继续减少 JS 编译工作不能解释或消除全部等待。W 包含事件调度及框架后续工作，不能直接标为“纯原生绘制耗时”，E 也不是屏幕显示完成时间。

最终小规模编译器优化只有桌面验证，没有新的设备耗时数据。固定槽位、额外背景图层和多套渲染路径仍缺少足够收益证据；本次审查没有改变此前不引入它们的判断。

以下事项没有设备证据，本报告不作为确定缺陷上报：受控 switch 拒绝变更后的原生复位、不同固件下滚动与 nextTick 的顺序、页面后台更新成本、真实显示完成时间和原生内存占用。只有后续改动实际涉及这些路径时，才需要一次聚焦的设备验证；上述已复现的逻辑问题无需再让用户逐版运行诊断包。

建议修复顺序是：存储事务与字符串键 → 两类缓存正确性和几何检查 → 发布失败重试与错误保留 → 文档入口。改动应配合各问题的针对性回归，保留现有性能路径，版本号继续保持不变。
