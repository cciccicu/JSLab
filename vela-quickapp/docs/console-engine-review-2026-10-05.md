# Console 运行器审查与 Console/UI 合并评估（2026-10-05）

本次是源码审查、逻辑复现和方案评估，没有修改生产运行逻辑，没有实施模式合并，也没有重新构建安装包或修改版本号。延续用户要求：优先处理常见、可低成本修复的问题，不为极端情况引入复杂机制，不以同时运行多个脚本为设计前提。

结论：适合统一脚本执行会话，推荐使用一个运行页面，在首次成功 `ui.render()` 时从 Console 切到 UI。两者目前已经使用同一个 Vela JS 环境和 `new Function`，差别是注入对象、生命周期管理和页面展示，并非两套独立的 JS 虚拟机。合并的主要价值是 API 一致、错误和资源管理一致，以及同一脚本可以同时使用日志与交互界面；不能直接推导出 2048 会进一步加速。

## 已确认的问题

### 1. [P2] 同步主体结束后被标为完成，停止和重跑没有管理旧计时器

位置：`run-console.ux:121`、`:179`、`:184`、`:231`、`:241`。

用户函数同步返回后，页面立即设为 `isRunning = false`、状态“已完成”，停止按钮消失，`onStop()` 也直接返回。`cancelRun()` 和重新运行只改变 `runId`，没有清理当前运行创建的计时器。

复现脚本：

```js
setInterval(() => {
  console.log('tick');
  system.files.writeText({ text: 'tick' }); // 审计中是记录调用的 mock
}, 10);
```

结果：

- 同步主体返回后显示“已完成”；调用 `onStop()` 不使当前 runId 失效。
- 后续 tick 仍调用文件接口。
- 在同一页重新运行一次后，存在两个 interval，每轮发生两次原生接口调用。
- 旧运行的 console 输出被 runId 检查拦住，但旧回调本身及其文件等副作用未被拦住，因此仅看日志可能察觉不到重复工作。

这不依赖用户主动同时运行两个脚本，是同一页面的一次重跑即可产生的问题。

范围必须说明：Vela 文档规定 `setTimeout` 等异步操作绑定页面，页面销毁后不再执行。本项确认的是**页面仍存在时的停止/重跑行为**，不是认定页面销毁后计时器仍会一直运行。现有帮助也明确要求脚本退出前释放系统订阅、媒体和计时器；不能把所有用户自管任务一概称为引擎泄漏。

建议把“同步主体已返回”和“会话已停止”分开。若继续提供停止/重跑，至少为注入的 `setTimeout`、`setInterval` 及对应 clear 函数建立当前运行的轻量记录，在停止/重跑时清理，并对旧回调检查会话是否仍有效。原生传输、传感器、音频等继续按明确的 API 契约由脚本释放，不引入所有系统调用的通用代理。单 JS 线程上，停止按钮不能抢占正在执行的同步死循环，不应承诺该能力。

### 2. [P2] 返回的 Promise 和异步回调错误没有进入运行页

位置：`run-console.ux:231`、`:232`；共享接口直通见 `scriptRuntimeApi.js:59` 附近。

`userFunction(...)` 的返回值被丢弃，catch 仅覆盖同步调用。原生 API 后续调用的 success/fail 回调也不在这层 try/catch 内。应用入口没有把这些错误转发给当前运行页的处理器。

两项复现：

```js
system.http.request({
  success() { throw new Error('callback failed'); }
});

// 独立复现：返回 thenable，观察运行器是否订阅失败。
return {
  then(resolve, reject) {
    reject(new Error('returned rejection'));
  }
};
```

第一项在 mock 后续调用 success 时抛出到运行器之外，页面仍为“已完成”，`error` 为空。第二项的 `then` 根本没有被调用。UI 控件回调已有返回 thenable 的错误处理，但 UI 页的顶层用户函数也没有观察返回值，这部分应在共享执行层一起处理。

建议至少捕获同步主体、返回的 thenable、受管计时器和 UI 事件回调的失败，统一送到有长度限制的错误展示。未返回的 Promise 链及任意原生回调不能靠一层外部 try/catch 自动捕获：需要脚本显式处理，或只对确有必要的 API 做针对性适配。不要宣称实现了一般性的异步异常隔离。

### 3. [P2] 合法的非 Error 抛出值会破坏错误处理，错误文本没有长度上限

位置：`run-console.ux:234`，编译失败分支另见 `:252`。

页面直接读取 `error.name`、`error.message`。实测：

| 输入 | 当前结果 |
| --- | --- |
| `throw null` | 错误处理自身再抛 TypeError；页面保留“运行中”，没有错误内容 |
| `throw 'boom'` | 显示 `undefined: undefined` |
| `throw new Error('x'.repeat(100000))` | 错误字段长达 100007 个字符 |

普通 Console 输出限制为 6144 个字符，但错误直接绑定到原生 text，绕过该限制。

建议共用一个小型错误格式化函数，处理 null、字符串和普通 Error，限制最终展示长度，并在转换失败时使用固定兜底文本。不要为异常对象实现深遍历或完整序列化；额外工作只发生在错误路径。

### 4. [P2] 日志限额没有限制前置格式化开销

位置：`run-console.ux:139`、`:144`、`:156`；对象预览位于 `:43`。

两种问题：

1. `args.map(formatConsoleArgument).join(' ')` 先执行，随后 `appendConsoleOutput` 才检查输出已截断。缓冲区填满后继续记录 100 次带 getter 的对象，getter 仍被读取 100 次，尽管日志全部被丢弃。
2. “最多 20 项”只作用于最外层数组/对象。单个字段包含 3000 项嵌套数组时，当前格式化仍读取 3000 次 getter，生成 60011 字符的临时字符串，再交给输出截断。根对象的 `Object.keys` 也会枚举全部键。

因此当前 6 × 1024 **字符**限制有效约束最终结果，不能限制为构造结果花费的 CPU 和临时内存。附加截断标记后，该复现最终显示字符串为 6154 字符，这个小差异不是主要问题。

建议先在日志入口检查缓冲区是否已满，再进行任何格式化。若要进一步保护大对象，使用有深度、元素数和文本长度预算的浅层预览，对更深对象显示摘要即可；没有必要支持任意复杂结构的 JSON 等价序列化。用户脚本自己提前构造字符串的成本，不在日志器能避免的范围内。

### 5. [P3] 一旦出错，错误前输出会被隐藏

位置：`run-console.ux:9`、`:10`。

```js
console.log('important context');
throw new Error('failed');
```

缓冲区和 `result` 仍保留 `important context`，但模板仅在 `!hasError` 时显示日志，因此用户看不到定位问题所需的前文。

建议保留日志区域，并在下方或独立错误卡片显示失败内容。普通成功运行无需增加日志复制或格式化；错误只增加一个有上限的展示块。

### 6. [P3] 会话失活后，已打开的对话框 Promise 可以一直 pending

位置：`src/utils/runtime/scriptDialogApi.js:12`；承诺见 `src/data/helpDocs.js:39`。

调用 dialog 前会检查活跃状态，但已有对话框的回调只有 `if (isActive()) resolve(...)`，会话失活时既不 resolve，也不 reject。复现为：创建 confirm → 会话失活 → 收到取消回调 → Promise 仍 pending。内置帮助却写着脚本退出时会 reject。

这是 Console/UI 共用的边界行为，正常完成对话框不受影响，实际优先级低于前几项；不能仅凭 pending 就推断存在永久内存泄漏。

合并会话时，可在统一 dispose 中处理唯一挂起的对话框，使其按约定结束；也需要考虑拒绝后用户 catch/finally 的清理行为。如果暂不提供退出时结算的保证，至少调整文档与实际一致。无须增加通用异步任务注册系统。

## 已有设计中应保留的部分

| 方面 | 判断 |
| --- | --- |
| 日志发布 | 80ms 合并发布、限制最终输出长度值得保留；问题在前置格式化与隐藏视图仍写响应式字段的潜在成本。 |
| 同步计时 | 当前文字明确写“同步运行耗时”，不是异步任务完成耗时或屏幕渲染耗时；编译也不在该计时段内，不应擅自赋予更多含义。 |
| 运行令牌 | runId 和 destroyed 检查能隔绝旧输出，应保留；不能将它等同于已经取消底层任务。 |
| 页面资源 | 页面的时钟和日志 flush timer 有销毁清理。页面 onHide 可能只是打开输入对话框，不应在此终止执行会话。 |
| 存储 | 延用上一轮已修复的队列和字典键实现，本轮没有重复修改。 |
| 布局 | 336×480 外壳、scroll 内容与后绘制工具栏沿用当前规范，没有发现需要为合并引入第二套布局引擎的理由。 |
| 系统接口 | 保持已声明 features 与可选接口兼容处理；不为合并新增原生权限。 |
| 信任模型 | `new Function` 共享应用 JS 环境，虚拟 console/window 只是注入对象，不是安全沙箱。不给用户脚本虚构强隔离承诺。 |
| 多实例边界 | 模块级 Console 缓冲和页面数据中的 vwindow 可以在提取会话时自然迁移；用户只运行一个脚本，当前不另建多脚本调度器。 |

没有设备数据证明 Console 的常规短日志路径是新的性能瓶颈。当前能确定的是多余序列化工作与重跑残留任务，不应把它们换算成未经测量的设备毫秒数。

## 合并方式比较

| 方案 | 状态与生命周期 | 成本与取舍 |
| --- | --- | --- |
| 单一会话、同页切换 Console/UI | 脚本只执行一次；计时器所属页面不变；signal 和闭包自然保留 | 推荐。复用 UI 编译与字段发布，页面仅切换展示分支。首次创建 UI 组件仍有成本。 |
| 独立 UI 页，`router.replace` 替换 Console | 旧页面销毁；文档规定旧页面所属异步任务不再执行 | 不能直接搬现有实现。必须设计任务归属与会话迁移；路由参数不能携带活函数。 |
| 独立 UI 页，`router.push` 保留 Console | 原页还在，但存在两个页面的显示、返回和销毁生命周期 | 可实现，但需要跨页会话容器、宿主挂接和释放规则，也会保留原页资源，暂缺少对应收益证据。 |
| UI 调用时跳页并重跑代码 | 初始化、随机状态、文件/网络副作用都会再执行，闭包重建 | 不采用。当前 run-ui 的 onInit 会读取并执行代码，不能直接把它当作接管既有会话的显示页。 |

依据来自仓库内 Vela 文档：

- `VelaDocs/docs/zh/guide/framework/script/lifecycle.md:56`：多页面共享 Context；`:96`：页面销毁后其关联的异步调用不再执行。
- `VelaDocs/docs/zh/features/basic/router.md:28`：params 的值统一转换为 String；`:74`：replace 销毁被替换页。
- `VelaDocs/docs/zh/guide/framework/template/if.md:51`：if/elif 为 false 会移除节点，show 只隐藏而保留节点。

没有禁止采用独立页面；只是对于当前只运行一个脚本、需要低复杂度和保持性能的目标，同页方案更直接。

## 推荐的具体行为契约

1. 所有脚本都注入 `console`、`ui`、`system`、`dialog`、`script`；不再以扩展名限制能否调用 UI。
2. 普通 `.js` 初始展示 Console；现有 `.ui.js` 初始展示 UI，保留兼容性并避免已知 UI 脚本先闪现 Console。扩展名只保留为启动偏好。
3. 首次成功 `ui.render()` 编译并由宿主接受后，自动切到 UI；单纯创建 signal、构造组件、设置标题或调用 showHeader 不触发切换。失败则保留当前视图并展示错误。这里“接受”不代表屏幕已经完成绘制。
4. 后续 console 输出进入有上限的普通 JS 缓冲，不自动抢回 Console 视图。用户可以通过运行器菜单查看日志并返回 UI；查看日志不重新执行脚本。
5. 用户主动查看日志后，普通 signal 刷新及后续 render 不应自动抢回 UI。自动切换是一次性的首次显示策略，返回 UI 由用户操作。
6. 隐藏 Console 时停止它的响应式 result 发布与 flush 定时任务；进入 Console 时一次同步缓冲内容。数据缓冲保留不等于隐藏原生 text 仍需要更新。
7. 两种展示分支使用 `if/elif`，避免仅用 show 留下两套原生树。脚本会话和 UI 源数据保留在响应式数据之外，不随分支销毁而丢失。查看日志时，UI 的原生发布可暂停；返回时必须用最新状态重新挂载，并使发布器快照与实际显示保持一致。切换的这一次挂载成本与正常每帧性能分别评估。
8. 停止、重新运行和页面销毁终止当前会话；切换视图、熄屏或打开 dialog 导致的 onHide 不终止会话。正常脚本主体返回只改变同步执行状态，不自动宣告所有任务结束。
9. 初期 `script.mode` 保留为启动模式，避免跟随当前可见视图反复改变已有脚本语义；帮助中明确它不再是 UI 能力开关。如需要暴露视图状态，应另行定义，不复用含义不同的旧字段。
10. 统一错误入口与保留规则。错误前日志仍可查看，排队的正常刷新不能立即清除错误；不把任意原生任务托管、同步代码抢占或沙箱化混入这次合并。

菜单和分支显隐属于实际产品改动，实施时需要完整处理全屏 UI、返回键及错误提示入口。以上为建议契约，当前代码尚未提供这些行为。

## 控制实现规模与验证范围

实现可以围绕一个轻量 `scriptSession` 展开：当前执行标识、输出缓冲、错误入口、受管计时器、共享 script/system/dialog API，以及现有 `createUiSession`。页面负责当前显示分支和原生事件；现有 `uiLayout`、`uiPublisher`、对象样式、稳定节点身份和字段更新保持不变。仅使用 Console 的脚本不应创建原生 UI 节点，不需要动态模块加载或 Proxy。

修复优先级建议为：

1. 日志满额前置检查、错误值格式化和限长、出错保留日志：改动小，额外工作主要位于错误路径，且能减少无效开销。
2. 共享执行边界：观察返回值、管理明确受管的计时器，修正停止/重跑状态。成本发生在任务创建、回调及停止处，无须修改 UI 编译器。
3. 同页模式合并，同时更新模式说明、帮助、类型声明、模板、编辑器入口及依赖这些能力说明的生成提示；避免只改运行页导致脚本仍被旧规则误导。
4. 单一挂起对话框的结束契约随会话 dispose 一并明确；不单独发展成跨页面任务框架。

没有建议增设 worker/独立 JS VM、自动改写循环、全面原生 API 代理、深比较缓存或另一套渲染器。这些都不符合本次收益与复杂度要求。

实现后的桌面回归应聚焦：重跑不累积受管任务、旧回调失效、返回 Promise 的失败、异常值与大日志、首次 UI 切换不重复执行、视图切换保留 signal/回调、隐藏日志不产生响应式发布、UI 重挂载显示最新值、对话框不误终止会话，以及原有 UI 性能回归。

桌面测试无法验证原生节点移除的真实内存收益、首次 UI 挂载延迟或设备显示完成。若实施合并，再用一次集中设备验证覆盖“普通脚本 → 异步 UI → 查看日志 → 返回 UI → 停止/重跑”和现有 2048 即可；当前审查无需用户继续逐版运行诊断包。
