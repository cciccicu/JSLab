# 了解 JSLab 原理

本文介绍当前实现，不代表所有早期版本都采用相同的内部结构。各功能的最低支持版本以[版本说明](installation.md)和对应 API 文档为准。

JSLab 怎样让一个 JavaScript 文件拥有原生交互界面？在手环上编辑代码时，怎样避免每次输入都重新处理整个文件？同一份脚本又怎样变成独立安装的快应用？

本页面向希望研究、扩展 JSLab 的开发者，深入介绍**脚本运行器（含 UI）、设备端编辑器、独立快应用打包**三项功能中的自研机制。阅读时只需要了解 JavaScript 的函数、对象和异步调用；文中会沿着实际的数据流，解释实现方式和设计取舍。

**项目源码：[cciccicu/JSLab · GitHub](https://github.com/cciccicu/JSLab)。** 每一节末尾都有源码阅读入口。具体的接口用法仍以 [运行环境与 API 总览](runtime-api.md)、[制作交互界面](ui-api.md) 和 [导出为独立应用](rpk-guide.md) 为准。

## 一、脚本运行器：从源码到原生交互界面

### 一次运行怎样建立

JavaScript 的解析和执行由设备上的 Vela 引擎完成。JSLab 自行实现的是包围这次执行的运行环境：创建脚本接口、管理日志和对话框、维护 UI 会话，并把脚本产生的界面交给原生页面显示。

运行页接收脚本名称和源码，用 `new Function` 创建函数，将 `console`、`ui`、`dialog`、`script`、`system` 作为五个参数传入。因此，脚本里对这些名称的访问，会落到本次运行提供的对象上。`system` 连接设备 API，`script` 提供脚本名称、数据存储和退出等能力，`ui` 则连接独立的界面会话。

脚本顶层代码执行完，不等于交互结束。按钮回调、渲染函数和信号仍可通过闭包保留脚本状态，等待之后的事件。运行页会捕获顶层同步异常，以及脚本返回的 Promise 拒绝；UI 事件入口也会处理回调抛出的异常和返回的 Promise 拒绝。这些入口不能代替脚本对所有异步任务的错误处理，例如自行启动但没有返回的 Promise 仍应显式处理失败。

会话对象保存在以页面实例为键的 `WeakMap` 中，函数、缓存和内部状态不会直接放进页面的响应式数据。页面数据主要承担可显示的内容：文字、节点坐标、尺寸和颜色。这一分工会贯穿整个运行器。

### UI 描述、布局结果和原生组件是三层不同的东西

下面的计数器可以直接作为脚本运行：

```js
const count = ui.signal(0);

ui.render(() => ui.column([
  ui.heading('计数器', { id: 'title' }),
  ui.text('当前次数：' + count.get(), { id: 'value' }),
  ui.button('增加一次', () => count.update(value => value + 1), { id: 'add' })
], { id: 'counter', gap: 8 }));
```

`ui.text()`、`ui.button()` 等方法先生成普通 JavaScript 对象。对象描述组件类型、内容、样式和回调，此时还没有创建屏幕上的按钮。`ui.render()` 接收这些描述，或者接收一个能够重新生成描述的函数。

接下来的数据流是：

```text
渲染函数读取脚本状态
  ↓
生成组件描述树
  ↓ compileUi
测量尺寸、排列位置
  ↓
生成扁平显示节点 + 独立的事件处理表
  ↓ UI 发布器
更新页面数据
  ↓
Vela 原生 text、switch、slider 等组件显示内容
```

这三层的职责分别是“表达界面”“计算怎样显示”和“实际显示”。JSLab 的运行页预先编写了原生组件模板，根据节点类型选择相应结构；嵌套的布局描述不会原样变成同样深度的页面组件树。按钮使用原生页面中的可点击容器，文字、开关、滑块和二维码等交给对应的原生组件。

这样的结构使脚本无需生成 `.ux` 页面，也无需在运行时编译新的页面模板。一个固定的运行页就能承载不同脚本的界面。

### 布局编译器怎样处理一棵树

`compileUi()` 分成测量和输出两个过程。测量阶段先确定可用宽度，再根据子项计算容器高度和相对位置。例如，`row` 会从可用宽度中扣除内边距、间距和指定宽度的子项，把剩余空间按 `flex` 权重分给其他子项；`column` 累加子项高度；`stack` 根据子项位置计算所需范围。

树的遍历使用显式的进入、退出工作项：先安排子项测量，等子项完成后再计算父容器。输出阶段同样使用工作栈，将相对位置累加成屏幕坐标。这样，布局嵌套不必依赖同样深度的 JavaScript 递归调用。编译器还会检查祖先链上的循环引用，避免把循环对象当成合法的布局树。

输出时，透明容器通常只参与布局；需要背景的容器会产生背景节点；叶子组件产生真正的显示节点。最终节点主要由字符串、数字和布尔值组成，便于比较，也减少了页面系统需要观察的对象层级。

文字高度有一个需要理解的边界：自动行数采用基于文字长度、字号和宽度的保守估算，具体换行与省略仍由原生文字组件完成。对于高度必须稳定的面板，显式设置 `lines` 或 `height` 更容易得到可预测的布局。

### 一次状态变化怎样减少重复工作

`ui.signal()` 保存一个值。`set()` 在新旧值相同时不安排刷新；值发生变化时，把会话标记为需要刷新，并通过 Promise 微任务排队。同一轮同步执行中、刷新任务开始之前的多次状态更新，只会安排一次刷新。

这里比较的是值或对象引用，不会深入比较对象的属性。原地修改一个对象，再把同一个对象交给 `set()`，不会触发刷新；这类状态可以传入新对象，或在修改后显式调用 `ui.refresh()`。

刷新仍会重新调用整个渲染函数，再把结果交给布局编译器。当前实现没有逐个追踪“哪个组件读取了哪个 signal”，所以渲染函数中的计算也会重新执行。昂贵的数据处理适合放在状态更新过程或自己的缓存中；渲染函数应专注于从当前状态生成界面，渲染期间修改 signal 会被运行层拒绝。

重新执行渲染函数后，还有两层复用机会：

| 层次 | 比较什么 | 能省下什么 |
| --- | --- | --- |
| 叶子测量缓存 | 组件 ID、可用宽度，以及影响显示的输入字段 | 未变化叶子的文字转换、样式计算和尺寸测量 |
| 编译结果复用 | 上一帧与当前帧节点的全部显示字段 | 保留相同节点对象，让会话快速判断显示结果是否变化 |

回调函数不参加叶子测量缓存比较。即使每次渲染都生成一个新的箭头函数，只要显示输入相同，测量结果仍可复用；事件处理表则会更新为这次渲染的回调。于是，按钮可以保持相同外观，同时使用最新的闭包。

缓存也有明确边界。可变对象或函数作为普通显示输入时，不走只比较基本值的缓存路径；每次编译会生成新的缓存集合，已经消失的组件不会一直占着缓存。布局位置变化时，会复制需要移动的旧节点再改坐标，避免提前改坏上一帧的记录。

### 为什么还需要一个 UI 发布器

布局编译完成后，结果还要进入 Vela 页面的响应式数据。即使新旧节点内容相同，反复替换整个数组或对象，也可能增加页面系统的观察和列表更新工作。因此，`uiPublisher` 保留一份普通 JavaScript 编译快照，并负责把差异写入页面。

当节点数量、顺序、ID 和类型都稳定时，发布器保留原来的页面数组与节点，只写入变化的字段。例如，计数器通常只需更新计数文字。当发生插入、删除或重排时，它按 ID 查找旧节点，在类型也相同的情况下复用对应的页面对象，再组成新的数组。

比较的依据是前后两份编译快照，而不是遍历读取页面上已经被观察的字段。这使“判断哪里变了”与“通知页面更新”分开。编译器内部字段也不会全部复制到页面，事件闭包则始终通过独立的处理表查找。

没有显式 ID 的组件会按布局路径生成 ID。静态界面通常可以使用这种方式；会插入、删除或重排的列表更适合给每项稳定且唯一的 ID，否则位置变化可能让同一项获得不同身份，减少复用机会。

### 出错、隐藏和退出怎样影响会话

界面可见时，新一帧的缓存和事件表要等宿主接受发布后才提交。显式调用 `ui.render()` 提交新界面时，运行层还会保留旧的渲染来源和已接受的帧；如果编译、发布或显示失败，会恢复这些记录，并在需要时尝试重新发布旧帧。这样可以避免失败的新布局立即取代原本可用的界面。

这种恢复针对界面会话，不会撤销脚本已经做过的文件写入或其他副作用，也不会回滚已修改的 signal 值。渲染函数保持无副作用，才能让失败后的重试容易理解。

切到日志或页面暂时隐藏时，UI 会话仍然存在。signal 刷新会先记下需要更新，恢复显示时再计算最新界面，或者重新发布缓存的帧。隐藏 UI 本身不会暂停脚本中的所有计时器与异步任务。运行页销毁时，会使会话失效、清除缓存和事件表、取消它拥有的对话框并释放日志缓冲。

这套生命周期管理也有边界：`new Function` 没有建立独立的 JavaScript 虚拟机，五个注入对象不是安全隔离边界；脚本自行创建的计时器、系统订阅等资源，也不能理解为都由 UI 会话自动接管。开发者仍需按相应 API 的约定停止不再使用的任务。

**源码阅读顺序：** 在仓库的 `vela-quickapp/src/pages/workspace/run/run.ux` 查看入口、原生模板和生命周期，然后进入 [运行层源码目录](https://github.com/cciccicu/JSLab/tree/master/vela-quickapp/src/utils/runtime)：`uiRuntime.js` 管会话，`uiLayout.js` 管布局和缓存，`uiPublisher.js` 管页面更新，`scriptRuntimeApi.js` 管注入接口。可以沿着“点击按钮 → `invoke()` → signal → `flush()` → `compileUi()` → `publishUi()`”跟踪上面的计数器。

## 二、设备端编辑器：把一次输入的影响限制在必要范围

### 文字模型与显示模型分别保存什么

手环上的代码编辑需要同时维护全文、光标、行宽、语法颜色和滚动位置。如果每次输入都重新分行、扫描全文，再把全部文字片段交给页面，字符很少的一次修改也会引发大量工作。JSLab 将这些责任拆开，并用一次编辑产生的变化记录连接它们。

| 数据层 | 主要内容 | 用途 |
| --- | --- | --- |
| 光标前后的源码 | `before`、`after` 两段字符串 | 保存编辑位置两侧的文字，供插入、删除、保存和运行使用 |
| 文档模型 | 带稳定 ID 的行记录、每行宽字符数量和宽度、光标位置 | 增量维护行结构和几何信息 |
| 高亮缓存 | 每行的输入状态、输出状态、文字和着色片段 | 判断哪些行需要重新扫描 |
| 页面显示数据 | 行与片段的显示键、文字、颜色，以及光标坐标 | 驱动原生文字组件和光标显示 |

文档模型与高亮缓存保存在页面之外的普通对象中。完整源码按需由前后两段拼接并缓存；编辑使这份缓存失效。高亮显示时，页面主要接收分行后的文字片段；普通文本显示时，页面接收完整文字。

### 插入一个字符，与插入一个换行有何不同

输入不含换行的文字时，文档模型保留当前行对象，只修改这行的文字、宽字符数量和宽度，并更新光标。其他行的身份不变，也无需重新创建整个行数组。

插入换行时，当前行保留换行前的部分，其余部分形成新的行记录；删除行首前的换行时，则把当前行并入上一行。编辑操作返回 `startLine`、`removedLines` 和 `addedLines`，告诉后续高亮与显示层从哪里开始处理、有哪些行结构发生变化。

稳定的行 ID 在这里很关键。插入换行会让后续行的行号变化，但没有参与拆分的行仍是原来的对象，高亮缓存仍能找到对应记录。显示层也可以插入新行，而不必为所有后续行重新建立身份。

移动光标走另一条路径：更新文档光标，把跨过的文字在 `before` 与 `after` 之间移动，再提交光标坐标和滚动请求。全文内容没有改变时，不必重新进行语法着色。

### 光标位置与内容宽度怎样计算

文档模型记录每行和光标之前的宽字符数量。对于当前字体配置，位置计算可以概括为：

```text
横向位置 = 普通字符计数 × 普通字符宽度
         + 宽字符计数 × 宽字符宽度
纵向位置 = 行索引 × 行高
```

这里的宽字符包括实现中识别的中文和全角标点等。每次从整数计数重新计算位置，可以避免连续插入、删除时不断累加小数宽度所产生的漂移。点击混合宽度的行时，模型从较近的一端查找字符边界；上下移动时保留希望到达的横向位置，减少长短行切换造成的光标偏移。

横向滚动范围还需要知道最长行。模型维护最大行宽及达到该宽度的行数；只有相关记录失效时才重新查找。如果反复删除同一条最长行，会缓存“其他行的最大宽度”，减少重复扫描。实际内容区宽度按一定步长预留空间，避免每多一个字符就调整所有行的显示宽度。

这是一套结合编辑器字体配置的宽度模型，位置索引沿用 JavaScript 字符串的 UTF-16 单元；不能把它理解为支持任意字体塑形和所有组合字符的通用文字排版引擎。

### 增量高亮怎样知道可以停止

JavaScript 的颜色不能完全按行独立计算。上一行是否打开了块注释、字符串是否跨行延续，会影响当前行应该怎样着色。JSLab 的词法扫描器为每行接收一个输入状态，返回文字片段和输出状态；下一行再使用这个输出状态。

当前状态以紧凑数值保存扫描上下文：一部分记录是否处于块注释或延续的字符串中，另一个标志辅助判断 `/` 是否可能开始正则表达式。扫描器负责容忍尚未写完的代码并着色，不生成完整语法树，也不承担 JavaScript 语法校验；模板字符串采用整体字符串着色。

高亮缓存记住每行的文字、输入状态和输出状态。编辑后，从受影响的行重新扫描，并把新的输出状态向后传递。越过直接修改的范围后，如果遇到某行的文字和输入状态都与缓存一致，后续分析就可以停止。

下面是省略缓存维护细节的流程示意：

```text
从受影响位置取得第一行及其输入状态
逐行向后处理：
    若已越过修改范围，且本行文字、输入状态等上下文均未改变：
        停止，沿用后续缓存
    否则：
        扫描本行并记录新片段
        用本行输出状态作为下一行输入状态
```

例如，把 `count = 1` 改成 `count = 2`，通常不会改变下一行的输入状态；在前面插入一个未闭合的 `/*`，则可能改变后续许多行，甚至必须扫描到文件末尾。**增量高亮减少的是与修改无关的重复扫描，不能保证每次只处理一行。**

还有一个容易遗漏的反向影响：标识符之后的下一段代码可能是 `(`，从而影响它是否按调用名称着色。如果改动改变了这个判断，高亮器会回看前一条相关的非空行，再开始向后传播。只从被编辑的行向后处理，会漏掉这类变化。

### 分析完以后，怎样减少原生列表更新

高亮结果通过 `commitHighlightedLines()` 写入页面。行结构没有变化时，保留原来的行对象；片段数量不变时，只修改实际变化的文字和颜色。新增、删除片段或行时，再对相应数组做局部调整。

这一层与词法缓存解决的是不同成本：词法缓存减少扫描工作，字段级提交减少页面系统的观察和列表重建。即使一个词被重新扫描，只要对应显示字段相同，也不必重复写入页面。

当字符数或行数超过用户设置的高亮阈值，或者着色片段超过内部预算，编辑器会退回普通文本显示。片段预算控制的是原生页面需要承载的着色片段数量，复杂的短代码也可能比更长的普通文字产生更多片段，因此只检查源码长度并不充分。

降级会减少语法着色相关的处理，不会截断源码，也不是脚本存储长度限制。当前显示方案仍可能把全文或全部高亮行交给页面，并没有只渲染可见行的虚拟列表。字符串拼接、换行时的数组调整、跨行状态传播和全文显示也仍有成本；超长单行、大量粘贴等场景不会因为采用增量模型就变成恒定耗时。

**源码阅读顺序：** 在 `vela-quickapp/src/pages/workspace/editor/editor.ux` 从 `insert()`、`remove()` 和 `updateCodeDisplay()` 入手，再进入 [编辑器源码目录](https://github.com/cciccicu/JSLab/tree/master/vela-quickapp/src/utils/editor)：`codeDocument.js` 管文字和光标模型，`javascriptLexer.js` 扫描单行，`javascriptHighlighter.js` 管跨行传播与页面提交，`codeEditor.js` 提供字体宽度计算。可以分别跟踪“输入一个数字”和“插入块注释起始符”，比较两次更新经过了多少行。

## 三、打包快应用：预编译引擎与内存装配

### 把固定引擎与用户脚本放在不同阶段处理

独立应用需要的原生页面、运行接口、对话框和存储逻辑，大部分在不同脚本之间相同；真正变化的是源码、应用信息、图标和少量选项。JSLab 因此把打包拆成两个阶段：开发者发布引擎时编译固定部分，用户导出应用时装配变化部分。

```text
引擎发布阶段
主项目运行层 → 同步到独立应用模板 → 按设备编译
            → 导出 template.zip 与 metadata.json

用户打包阶段
选定设备模板 + 脚本 + 应用信息 + 签名材料
            → 内存中替换资源 → 重建摘要并签名 → RPK

设备启动阶段
读取内嵌脚本数据 → 创建同类运行会话 → 执行脚本并显示 UI
```

完整的快应用工具链只参与引擎发布阶段。用户每次点击打包时，服务器不再生成临时工程并运行整套编译工具，也不执行用户脚本；它处理的是资源缓冲区和签名结果。

这里“编译”针对的是固定的快应用外壳。用户的 JavaScript 源码仍作为字符串保存在包中，到设备启动时才交给脚本运行器执行。打包本身不会把源码转换为机器码，也不提供源码加密。

### 模板怎样与主项目保持一致

`vela-rpk-template` 从主快应用同步运行时、脚本存储、对话框、输入组件等代码，运行页则通过脚本派生出独立应用版本。派生时只调整独立应用需要的入口与行为，例如从内嵌数据加载脚本、退出应用、展示关于页，以及应用打包选项。

同步脚本会检查预期修改位置是否存在。如果主运行页结构变化，旧的替换规则不再适用，构建会明确失败，要求维护者更新适配逻辑。源码同步检查还能发现模板中的引擎文件是否落后于主项目。

模板按目标设备分别编译，保留各自的布局资源和 `designWidth`。导出时会记录模板 ZIP 的 SHA-256 摘要、模板源码摘要和设备覆盖文件摘要。发布前的检查用这些记录验证模板是否对应当前源码；服务器加载模板时再检查 ZIP 摘要、格式、设备标记与设计宽度，避免装配到错误或损坏的引擎资产上。

这意味着，运行引擎修改后需要重新生成并发布模板。仅替换主项目的 JavaScript 文件，不会让已经预编译或已经安装的独立应用自动获得新引擎。

### 一次打包怎样改写资源

云端按目标设备缓存已加载的固定模板。每次打包创建自己的资源映射，替换本次需要变化的文件；固定资源可以复用读取结果，用户内容不会写回共享模板。

| 资源 | 本次装配做什么 |
| --- | --- |
| `manifest.json` 及相应变体 | 写入包名、应用名、版本和作者等信息 |
| `common/payload.json` | 保存脚本名称、源码、应用信息和打包选项 |
| `app.js` | 在预留位置内嵌 manifest 和脚本数据的 JSON 字符串 |
| `common/logo.png` | 有自定义图标时替换图标 |
| `META-INF` 中的元数据 | 根据最终资源重新生成摘要和签名所需内容 |

为什么既有 `payload.json`，还要把数据内嵌到 `app.js`？部分固件通过文件 API 读取包内 JSON 资源时存在兼容性问题。启动入口直接解析内嵌字符串，就不需要依赖这条读取路径；关于页也能使用同一份已加载数据。

本次装配使用内存缓冲区，不在服务器磁盘创建用户脚本工程、签名临时文件或临时 RPK。这个约束针对打包过程，云空间保存文件仍有它自己的存储流程。

### 源码怎样穿过 JSON 和 JavaScript 两层边界

把源码写进预编译的 `app.js`，需要处理两个嵌套层次。源码先成为 payload 对象的 `code` 字段，整个对象序列化为 JSON；这段 JSON 又要成为 `app.js` 中合法的 JavaScript 字符串字面量，所以还要再序列化一次。

```text
脚本源码字符串
  → 放入 payload.code
  → JSON.stringify(payload)，得到 JSON 文本
  → 再对该文本做字符串转义
  → 替换 app.js 中的固定占位字符串

设备启动后：
  JavaScript 还原内嵌字符串 → JSON.parse → 取得原始 code
```

这样，源码里的引号、反斜杠和换行仍然是数据，不会意外结束外层字符串。实现还显式转义 Unicode 行分隔符 U+2028 与 U+2029，并检查每个预留标记恰好出现一次，防止模板结构变化后替换错位置。

替换操作使用返回文本的回调函数。这个细节可以避免源码中的 `$&` 等内容被字符串替换函数当作特殊替换语法解释。整个过程的目标是保留源码原文，而不是在云端解析或执行脚本逻辑。

### 改完资源，为什么必须重建摘要和签名

安装包中的 manifest、源码或图标一旦变化，旧包中用于校验内容的记录就不再对应最终文件。JSLab 会先对装配后的资源计算 SHA-256 摘要，把文件路径与摘要写入 `hash.json`，再构造 `META-INF/CERT` 所需的内容。

签名阶段沿用快应用工具链的包格式实现：先对这份元数据签名，再汇集资源与相应摘要，生成最终包的签名结构。JSLab 使用从 `@aiot-toolkit/aiotpack` 适配出的内存签名代码；这里自研的是模板同步、资源装配和运行入口衔接，并未另行设计一种签名算法。

摘要回答“文件内容是否与记录一致”，签名把这些内容与签名身份关联起来，两者都不会隐藏源码。包名、版本和签名材料也各有作用：包名标识应用，版本信息用于区分更新，后续更新需要继续使用对应的签名材料。因此，修改源码后应重新打包并签名，不能直接改最终 RPK 中的文件再分发。

### 独立运行保留了什么，又改变了什么

独立应用带着运行器、原生页面和脚本一起安装，因此不要求设备上另有 JSLab。脚本仍得到 `console`、`ui`、`dialog`、`script`、`system` 五组接口，UI 描述与状态更新沿用前文介绍的运行机制。

应用外壳会应用导出选项。例如，关闭日志时仍保留 `console` 方法，避免旧脚本因为方法不存在而报错；隐藏顶栏的选项则由独立应用外壳约束。脚本的数据和设置归属新应用自己的存储空间，JSLab 中已有的数据不会自动迁入。

能成功装配并签名，说明打包流程完成；它没有实际执行脚本，也不能替代目标固件上的运行验证。设备支持哪些系统能力、脚本自身是否正确，以及运行时需要多少内存，仍由应用在目标设备上的实际执行决定。
